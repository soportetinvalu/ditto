# Diagnóstico de Accesibilidad sin Terminal

En **Ajustes → Copiar diagnóstico**, o en el aviso de Accesibilidad → **Copiar diagnóstico**, la app copia un informe de texto y guarda la misma información en:

`~/Library/Logs/MemoriaLocal/diagnostico-accesibilidad.txt`

El informe incluye versión/commit, macOS, rutas, PID, identificador, confianza AX, comprobaciones de firma dinámica y estática (normal/estricta), errores de Security, cdhash, flags, Team ID, entitlements, presencia de quarantine, número de instancias y Rosetta. Copiar el informe no solicita permisos ni modifica quarantine, TCC o las preferencias de seguridad. Registra si el botón **Solicitar permiso** invocó `AXIsProcessTrustedWithOptions` con `kAXTrustedCheckOptionPrompt=true`, cuántas veces y la última fecha UTC **en el proceso actual** (se reinicia al salir). Invocar la API no demuestra que macOS haya mostrado su aviso ni que el usuario lo haya concedido.

**Privacidad:** no lee ni incluye el historial ni el contenido anterior del portapapeles. Sí incluye rutas locales que pueden contener el nombre de usuario. Al copiar sustituye el portapapeles actual (también la copia seleccionada que provocó el aviso). Esa escritura se marca como propia para no capturar el diagnóstico en el historial, incluso si se copia durante la pausa y se reanuda después. El archivo se sobrescribe, con permisos 0600 y directorio 0700. No se envía por red.

## Solicitud oficial y comprobación automática

1. Con el pegado automático activado, selecciona una copia y pulsa **Solicitar permiso** si aparece el aviso de la app. Solo ese botón llama a `AXIsProcessTrustedWithOptions` con `prompt=true`; abrir Ajustes, arrancar la app, copiar el diagnóstico y los sondeos no lo hacen.
2. En el aviso de macOS abre Ajustes del Sistema y activa Memoria Local en **Privacidad y seguridad → Accesibilidad**. Si no aparece el aviso: quita la entrada de Memoria Local con **−**, vuelve a la app y pulsa otra vez **Solicitar permiso**. No la añadas con **+** en este intento.
3. La app consulta `AXIsProcessTrusted()` cada segundo durante un máximo de 60 s, también dentro de su aviso modal. Recomprueba al volver a primer plano, incluso tras agotar el sondeo mientras siga abierto ese aviso. Al detectar true cierra el aviso e informa **Permiso concedido**. Por seguridad no conserva un pegado pendiente: selecciona de nuevo la copia para pegarla.
4. **Solo copiar** cancela la espera. **Copiar diagnóstico** también termina la espera y sustituye el portapapeles por el informe. **Abrir Accesibilidad** sigue disponible como acceso a Ajustes, sin invocar el prompt. Si AX ya es true, no se muestra el aviso propio.

### Límites de la investigación

- `9c61aaa` retiró la llamada oficial que existía anteriormente; `8ed50be` solo añadió consejo de translocación/ruta, y `0cc9bb4` corrigió los flags de Security. La omisión está confirmada, pero no prueba por sí sola por qué una entrada añadida manualmente en el Mac devolvía false.
- [Apple documenta](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions) que el prompt es asíncrono y no modifica el retorno inmediato. No garantiza que cada invocación muestre otro aviso, ni que repare una entrada obsoleta.
- [Soporte Apple](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac) contempla añadir apps a mano. No se encontró una regla Apple específica de macOS 15/26 que invalide todas las altas manuales para firmas ad hoc hasta invocar la API. Tampoco una exigencia universal de ejecutar `lsregister`; [Launch Services](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCConcepts/LSCConcepts.html) registra las apps al abrirlas con Finder. Se mantiene abrir la copia instalada desde Finder, sin modificar registros desde la app.
- El [bundle ID debe identificar una sola app](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleidentifier), pero no sustituye una identidad de firma estable. [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) explica que el designated requirement ad hoc se liga a esa versión del código. [Quinn/DTS](https://developer.apple.com/forums/thread/730043) desaconseja mezclar builds ad hoc y Developer ID con el mismo bundle ID. Es una limitación fundada entre builds, no una prueba de la causa residual en este Mac.
- El [foro Apple 131322](https://developer.apple.com/forums/thread/131322) describe interruptor activo pero AX false después de actualizar, y propone quitar/reincorporar. Es compatible con autorización obsoleta, pero no demuestra una fila huérfana que «sombree» otra en este Mac. Ajustes permite ver nombres/interruptores y quitar entradas con **−**, no inspeccionar `csreq`, cdhash ni filas internas; sin Terminal no se puede demostrar ese estado interno. El nuevo diagnóstico comprueba el proceso, no lee la base TCC.
- No se añade `NSAccessibilityUsageDescription`: no figura en el catálogo Apple de [recursos protegidos](https://developer.apple.com/documentation/bundleresources/protected-resources), ni se encontró una clave oficial para personalizar el texto de este permiso AX en Tahoe. `NSAppleEventsUsageDescription` no corresponde a enviar CGEvent. Se conserva el nombre de la app en Info.plist y la explicación propia; el texto y la aparición del aviso oficial los decide macOS.

Los foros Apple directos devolvieron Security Verification; las citas de esos hilos proceden de extractos indexados, no de una lectura completa. Documentación API, TN3127, Launch Services y soporte Apple sí se recuperaron completos. StackOverflow 43348641 se contrastó por API: respuestas 56588476 (score 12) y 79939955 (score 0), ninguna aceptada; no se usa como solución verificada para Tahoe.

## Interpretación

- Un error de `SecCodeCheckValidity` o de `SecStaticCodeCheckValidity` identifica un problema de firma en la copia que se está ejecutando; compartir el código exacto, no suponer que todos los errores significan lo mismo.
- `SecCodeCopySigningInformation` describe la firma, pero su éxito no prueba su validez. Se consulta después de intentar validar y se conserva cualquier error.
- Firma válida y `AXIsProcessTrusted(): false` **no** demuestran que Accesibilidad esté concedida al proceso, aunque el interruptor esté activo. La firma ad hoc no da una identidad estable entre builds. Apple recomienda una identidad de firma estable para reducir problemas de TCC.
- El artifact `12046474023` se inspeccionó sin macOS: recursos SHA-1/SHA-256, `Info.plist`, requirements, CodeResources y páginas del ejecutable coinciden. Es arm64, tiene LC_UUID, identificador `local.memorialocal.app`, flags ad hoc `0x2`, sin entitlements ni linker-signed. El ZIP interior creado con `ditto` conserva permisos. **No se encontró una firma rota por el empaquetado.** Esto no valida la copia instalada ni permite atribuir su fallo a un bug de Tahoe.
- El empaquetado incorpora el commit antes de firmar y ahora comprueba la integridad del ZIP, lo extrae con `ditto`, comprueba el ejecutable y repite `codesign --verify --deep --strict`. No añade `--deep` al firmado: no hay código anidado y no es necesario para sellar recursos.

No repetir indefinidamente quitar/añadir el permiso si ya se hizo sin éxito. Compartir el texto de este botón permite distinguir firma instalada inválida de un problema de autorización sin pedir comandos al usuario.

Referencias: [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), [Quinn sobre TCC y firma estable](https://developer.apple.com/forums/thread/721745), [TCC y designated requirements](https://developer.apple.com/forums/thread/730043), [por qué no firmar con --deep](https://developer.apple.com/forums/thread/129980).
